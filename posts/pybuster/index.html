PyBuster: Building a Directory Enumeration Tool

pythonsecurity

PyBuster is a multithreaded directory and file enumeration tool for web servers. It brute-forces paths using a wordlist to discover hidden directories and files. I originally built it as part of an Ethical Hacking course at AUB, then cleaned it up and rewrote it as a standalone tool.

This isn't meant to replace tools like gobuster or dirb. They're faster, and heavily tested. The point was to understand how directory enumeration actually works: what requests to send, how to handle the responses, and what actually counts as a discovered path.

How it works

The tool reads a wordlist and appends each entry to the target URL as a path. For each path, it sends an HTTP GET request without following redirects. Non-404 responses get printed with their status code and content length. A thread pool handles multiple requests concurrently to speed things up.

Recursive scanning

Recursive mode is a big part of the tool. When the scanner discovers a directory (indicated by a 301 redirect or a 200 on a path ending with /), it re-queues the entire wordlist under that new directory. So if the wordlist has admin and the scanner finds /docs/, it automatically queues /docs/admin/. 

if args.recursive and is_directory:
    normalized = path if path.endswith("/") else path + "/"
    if normalized not in visited_dirs:
        visited_dirs.add(normalized)
        for word in wordlist:
            queue.put(normalized + word + "/")
        progress.total += len(new_paths)
        progress.refresh()

A set of visited directories prevents infinite loops. The progress bar total gets updated every time new paths are queued so it always reflects the actual remaining work.

Status code filtering

Sometimes, web servers can return unwanted codes like 403 in case of lack of authorization. Some servers also return error pages with a 200 status code. When scanning you might not care about that, so the tool supports filtering status codes. The tool also reports content length for each result, which helps spot false positives. A server might return 200 on every path but the error page is always the same size, so you can get some insights from the size of the returned page.

What I'd do differently

Python is probably not the best language to build a tool like this. The requests library is also not ideal since it doesn't support async HTTP requests out of the box. A library like httpx would be more suitable. Python also has the Global Interpreter Lock (GIL), a mutex that only allows one thread to execute at a time, so you don't get real parallelism like you would in other languages.

Since this tool is not meant to compete with established tools, I didn't focus on optimizing for performance or handling every edge case. For a production tool, a language like Go would make more sense: it compiles to a single static binary with no dependencies, goroutines are lightweight enough to run thousands concurrently, and there's no GIL which means real parallelism out of the box.

The tool works by treating any non-404 response as a valid page. But 404 is just a convention. A misconfigured server could return 404 on real pages or 200 on everything. A smarter approach would be to request a path that definitely doesn't exist, like /asjwiufhiwfhwfdjfh, record its response size as a baseline, and filter out any result that matches.
